# AWG Local Proxy — инструкция для Codex

**Дата:** 30 октября 2026 года.  
**Основной каталог:** `C:\dev\GO\AwgLocalProxy`.  
**Платформа первой версии:** Windows 11 x64.  
**Режим:** локальный прокси для приложений, которые пользователь настраивает самостоятельно.  
**Статус:** требования и план реализации, а не готовый или проверенный VPN-клиент.

## 1. Задача и обязательные ограничения

Разработай AWG Local Proxy: небольшой Windows-клиент с графическим интерфейсом и системным треем. Приложения подключаются к `127.0.0.1:1080` по SOCKS5 или, при включении пользователем, к `127.0.0.1:8080` по HTTP proxy. Прокси-компонент передаёт их TCP-соединения через AmneziaWG на уже существующий сервер пользователя. Другие приложения Windows продолжают работать как раньше.

Это **вариант А**. Раздел «Приложения» — помощник настройки прокси и запуска приложений, а не механизм перехвата трафика по EXE.

Не создавай TUN/TAP/Wintun-адаптер, не устанавливай сетевые драйверы, не используй WFP/WinDivert/инъекции DLL. Не изменяй маршруты Windows, системные DNS, WinINET/WinHTTP proxy, PAC, системные переменные HTTP_PROXY/HTTPS_PROXY/ALL_PROXY и правила брандмауэра. Не требуй повышения прав для обычной работы. Не добавляй службу Windows. Не изменяй конфигурацию сервера пользователя.

Наличие `AllowedIPs = 0.0.0.0/0` внутри конфигурации userspace-ядра **не означает**, что нужно добавлять системный маршрут: настройка относится только к внутреннему стеку. Не переноси команды `wg-quick` на хост.

Не пиши собственную криптографию или реализацию AmneziaWG. Не заменяй ядро на обычный WireGuard. Не обещай, что весь трафик любого выбранного EXE защищён: приложение может не учитывать прокси для части соединений.

## 4. Технический стек и границы компонентов

**Базовое решение:** Go + стабильная Fyne v2 для GUI; отдельный процесс `awg-proxy-core.exe` из fork. Перед фиксацией версии сделай короткий Windows-прототип: окно, tray, масштабирование и закрытие. Fyne документирует системный трей Windows и требует корректного вызова UI API из фоновых goroutine. [S7–S8]

Не добавляй Electron, браузерный frontend, веб-сервер управления или второй язык без конкретной необходимости. Fyne — не набор WinUI-контролов; не называй интерфейс полностью нативным WinUI. C toolchain/CGO могут требоваться для **сборки** GUI; это не требование установить компилятор на компьютер пользователя.

Версию Go выбери поддерживаемую на дату выполнения и совместимую с зависимостями. В проверенном upstream `go.mod` указаны `go 1.25.0` и `github.com/amnezia-vpn/amneziawg-go/v3 v3.1.20260828`; это исходная точка, а не указание использовать устаревший toolchain. Суффикс Go-модуля `/v3` не доказывает версию протокола сервера. [S2]

## 5. Проверка и доработка прокси-компонента

Все изменения этого раздела выполняются только после снятия лицензионной блокировки.

### 5.1. Что уже есть и что нельзя предполагать

README и `main.go` используют `netstack.CreateNetTUN`, `device.NewDevice` и `tnet.DialContext`; это внутренний виртуальный интерфейс userspace-стека, не установка TUN Windows. Присутствуют SOCKS5 TCP CONNECT, HTTP CONNECT и обычный HTTP forward. SOCKS5 BIND и UDP ASSOCIATE не реализованы. Есть импорт INI `.conf` и распаковка `vpn://` экспорта. [S1, S3]

Готовность Windows-сборки, стабильность и совместимость с конкретным сервером пользователя не проверены. Поддержку AmneziaWG 1.x и 2.0 подтверждай отдельными тестами, а не только наличием полей в README.

### 5.2. Начальный аудит

Собери неизменённый разрешённый к использованию commit; запусти его тесты. Зафиксируй Go, module graph, target GOOS/GOARCH и результат. Не исправляй всё одновременно.

По просмотренному коду проверь как минимум:

- `vpn.go` распаковывает zlib через `io.ReadAll` без явного лимита — добавь ограничение исходного файла и распакованного JSON; не доверяй длине из заголовка qCompress.
- `config.go` нормализует имена полей, а `ipcString` передаёт фиксированный набор параметров — добавь явную диагностику неизвестных/неподдерживаемых значений, иначе можно потерять параметры нового протокола.
- Проверь длину ключей, диапазоны значений, повторяющиеся поля, MTU, endpoint и несколько Peer. Не полагайся исключительно на ошибки нижнего слоя.
- Текущий `main.go` вызывает `log.Fatalf` в разных точках — организуй возврат типизированных ошибок и освобождение уже открытых ресурсов.
- `device.Up()` означает запуск устройства, а не успешный handshake; запись «listening» до фактического bind тоже не доказательство готовности.
- Проверь все HTTP-пути, CONNECT, proxy headers, half-close, тайм-ауты и завершение соединений. Не используй `http.DefaultTransport` с прямым Dial.

Это направления аудита, не заявление о подтверждённой эксплуатируемости всех перечисленных участков.

### 5.3. Прокси первой версии

SOCKS5 на IPv4 loopback `127.0.0.1:1080` включён по умолчанию. HTTP proxy `127.0.0.1:8080` отключён до включения пользователем. Порты настраиваемые; конфликт порта — понятная ошибка, без самовольного выбора другого порта и завершения чужого процесса.

Запрещены listeners на `0.0.0.0`, `[::]`, сетевом hostname или внешнем адресе. IPv6 loopback `[::1]` можно добавить отдельно после тестов; он не должен превращаться в dual-stack wildcard.

Реализуй/проверь TCP CONNECT, корректную обработку доменного имени, IPv4/IPv6 адреса, HTTP CONNECT и обычного HTTP forwarding. HTTP TLS не расшифровывать, сертификаты не подменять. UDP ASSOCIATE/BIND возвращают корректный отказ протокола, не изображают поддержку.

Вся сеть адресов назначения идёт только через netstack. При ошибке — отказ, без `net.Dial` через хост и без системного прокси из переменных среды. Никакого автоматического DIRECT fallback.

Ограничь число одновременных соединений, время handshake прокси, размер HTTP-заголовков, IPC-сообщений, входных конфигураций и диагностических логов. При корректном завершении закрывай listeners, активные потоки, netstack и устройство; не оставляй goroutine/process leak.

### 5.4. DNS и исключения

Доменные имена, полученные через SOCKS5/HTTP, разрешаются DNS внутри туннеля. Не используй для них `net.DefaultResolver`, DNS Windows или публичный DoH напрямую. Для проверок curl применяй `--socks5-hostname` или `socks5h`, а не `--socks5`, который может разрешить имя на клиентской стороне.

Если само приложение передало уже готовый IP после собственного DNS-запроса, прокси не может отменить этот запрос. Это нужно объяснить пользователю. Также прокси не контролирует неподдерживаемый UDP, WebRTC, QUIC и программы, игнорирующие настройки.

Допустимые прямые соединения **самого core**: UDP к endpoint VPN; при endpoint в виде имени — его bootstrap DNS через системный resolver. Это исключение относится только к имени VPN-сервера. Зафиксируй его в документации и тестах. Для желающих исключить bootstrap DNS — числовой endpoint, без скрытой подстановки чужого DNS.

Отсутствие DNS в конфигурации обрабатывай явно: предложи указать numeric DNS или сообщи невозможность разрешать имена. Не подставляй адреса молча. Проверяй достижимость DNS через AllowedIPs. DNS error, NXDOMAIN, отсутствие IPv6 или непокрытый AllowedIPs адрес не должны вести к прямому выходу.

### 5.5. Конфигурации и AmneziaWG 2.0

Импортируй клиентский `.conf`; поддержка `.vpn`/`vpn://` — только с проверкой реальной структуры, лимитами и тестами. Не сохраняй весь административный экспорт Amnezia, SSH-пароли и серверные ключи: извлекай только требуемый клиентский профиль и предупреждай об административных данных.

Сохраняй исходные значения Jc/Jmin/Jmax, S1–S4, H1–H4, I1–I5 и других обнаруженных в профиле параметров без самостоятельного «улучшения». Проверяй их по исходникам/документации **зафиксированной** версии движка. Не объявляй все поля из актуального README обязательными для AWG 2.0.

Неизвестные параметры не отбрасывай молча. Опасные `PreUp/PostUp/PreDown/PostDown` не выполняй ни при каких условиях. Системные параметры wg-quick `Table`, `SaveConfig` и подобные не должны изменять Windows; показывай, что они не применяются. Не передавай неизвестные параметры в shell.

Для первой версии достаточно одного активного профиля с одним Peer. Импорт нескольких Peer либо реализуй и протестируй полностью, либо отклоняй с понятной причиной; не выбирай первый тайно.

В тестовой матрице отдельно укажи: формат, семейство протокола, версию клиента/сервера, версию go-модуля, набор параметров, handshake и реальный HTTP-запрос через туннель. Без конфигурации пользователя результат подключения к его серверу помечается «не проверено».

## 6. Управление core и контракт IPC

Добавь в форке отдельный режим управления через наследуемые stdin/stdout pipes. Это **новая функция**, не существующий флаг upstream. Возможное имя флага: `--control-stdio`; окончательное имя зафиксируй в контракте.

Протокол: ограниченные по размеру NDJSON-сообщения с полями `protocol_version`, `type`, `id`, `payload`; типизированные команды и ответы. Не используй JSON-RPC-терминологию, если реализуешь не сам стандарт JSON-RPC. stdout — только протокол, stderr — только санитизированные логи. Не смешивай их.

Команды: `hello`, `validate_config`, `connect`, `disconnect`, `get_status`, `shutdown`. События: изменение состояния, ошибка, счётчики и handshake timestamp. `hello` возвращает версию протокола, версию core, commit и capabilities; неизвестная основная версия — отказ подключения.

В рабочем режиме GUI передаёт конфигурацию из памяти через stdin. Не передавай её через аргументы, environment, clipboard, URL или временный plaintext-файл. В ответах не должно быть PrivateKey/PresharedKey, полного IPC UAPI dump, исходной `.vpn` строки и ненужных идентификаторов сервера.

Состояния: `Stopped`, `Starting`, `Connecting`, `Connected`, `Degraded`, `Reconnecting`, `Stopping`, `Error`. Отдельно показывай «локальный порт открыт» и «туннель подтверждён». `Connected` требует подтверждённого handshake и успешной короткой проверки через туннель; внешний сервис проверки должен быть явно указан в настройках. Не включай постоянный скрытый опрос сторонних сайтов.

Не объявляй разрыв только из-за давнего handshake при простое: учитывай активность, попытки передачи и результаты проверки. При отсутствии handshake показывай ожидание/ошибку по тайм-ауту. Тайм-аут, отмена и повторное Connect не должны порождать параллельные core.

Supervisor запускает core только по абсолютному проверенному пути через Go `exec.Command`, не через shell. Защити от подмены бинарника через PATH/current directory. Сверяй manifest/hash и версию перед запуском; один хеш из неподписанного скачанного архива не доказывает подлинность источника.

При EOF control pipe, смерти GUI или команде Quit core должен прекращать работу. Для Windows рассмотри Job Object с kill-on-close; проверь совместимость запуска из Codex/терминала, где уже может быть Job Object. Завершай только созданный дочерний процесс, не все процессы с похожим именем.

Автопереподключение — ограниченный exponential backoff с jitter и отменой. Никакого прямого fallback. Смена профиля: остановка старого, закрытие соединений, запуск нового, проверка состояния. Старые соединения не мигрируют автоматически на новый сервер.

## 7. Хранение профилей и безопасность

Метаданные и настройки: `%LOCALAPPDATA%\AwgLocalProxy`. Секретная конфигурация шифруется Windows DPAPI с областью текущего пользователя; не применяй машинную область `CRYPTPROTECT_LOCAL_MACHINE`. DPAPI обычно связывает расшифровку с учётными данными пользователя и компьютером, но не защищает от вредоносного процесса с теми же правами. [S9]

Отдели metadata от encrypted profile blob. Для файлов и каталогов установи корректные Windows ACL; `chmod 0600` не замена Windows ACL. Запись атомарная, есть version/schema и безопасная миграция. Повреждение профиля не ведёт к незашифрованному сохранению.

Не обещай абсолютное стирание ключей из памяти Go/Windows: минимизируй время жизни и копии, по возможности очищай byte buffers, не включай секреты в дампы и отчёты. Импорт не удаляет пользовательский оригинал файла без отдельного действия.

В репозитории/артефактах/Actions запрещены реальные `.conf`, `.vpn`, private keys, PSK, SSH-данные, дампы трафика и пользовательские логи. Пример `.conf` содержит заведомые placeholders, не случайно реальные credentials. Перед каждым push и release — secret scan и проверка staged файлов.

Loopback без аутентификации означает доступ другим локальным процессам, иногда другим пользователям этой машины. Это **не** строгий allowlist приложений. Зафиксируй ограничение в модели угроз. SOCKS username/password и HTTP proxy auth можно добавить как отдельную опцию, но не обещай изоляцию от процесса, выполняющегося от имени того же пользователя.

Телеметрия и автоматическая отправка логов отсутствуют. Диагностика локальная, с ротацией и маскированием ключей, профилей, адресов посещаемых ресурсов. В обычном логе не записывай все домены пользователя. Публичный issue создаётся только из просмотренного пользователем очищенного отчёта.

## 8. Интерфейс и настройки приложений

### Основное окно

Русский интерфейс, строки вынесены для возможной локализации. Компактное окно без декоративного dashboard: профиль, фактическое состояние, одна основная кнопка Connect/Disconnect, SOCKS5/HTTP адрес с Copy, краткая ошибка и переход к диагностике. Различай счётчики TCP-полезных данных и зашифрованного транспорта; не выдавай их за одно и то же.

Разделы: «Подключение», «Профили», «Приложения», «Настройки», «Диагностика», «О программе». Не показывай private key в основном интерфейсе. Добавь импорт, переименование и удаление профиля; удаление активного профиля требует остановки и понятного подтверждения.

Tray: открыть, подключить/отключить, выбрать профиль, завершить. Закрытие окна по умолчанию скрывает его в tray с однократным объяснением; «Завершить» останавливает core. Повторный запуск показывает существующее окно, не открывает ещё один listener.

Автозапуск при входе Windows и автоподключение — раздельные опции, по умолчанию выключены. Используй только обратимые настройки текущего пользователя, без планировщика с повышенными правами. При запуске минимизируй скрытое сетевое поведение.

Проверь 100/125/150/200% DPI, тёмную/светлую тему, длинные русские сообщения, клавиатуру, фокус, табуляцию и screen reader. Не утверждай полную accessibility без проверки конкретной Fyne-сборки. Фоновая сеть/IPC не блокирует UI; обновления виджетов проходят через механизм UI-dispatch выбранной версии Fyne.

### Раздел «Приложения»

Встроенные карточки инструкций: браузер, Telegram, VS Code/Codex и «Другое приложение». У карточки есть название, способ настройки, адрес прокси, кнопка копирования и предупреждение об ограничениях конкретного приложения.

Для поддерживаемых программ можно создавать отдельный launch profile: абсолютный путь EXE, проверенный набор аргументов, отдельный browser user-data directory. Учитывай single-instance браузера: запуск с новыми аргументами не должен незаметно переиспользовать обычный профиль и игнорировать proxy flags. Не закрывай уже работающий браузер без согласия.

Аргументы и proxy behavior проверяй по актуальной документации конкретной программы. Не обещай, что единая переменная окружения проксирует весь VS Code, все расширения и дочерний Codex. Допустима копируемая инструкция; автоматическое редактирование существующих пользовательских профилей и реестра без отдельного действия запрещено.

Не запускай произвольную командную строку через `cmd /c`/PowerShell из поля настроек. Храни путь EXE и список аргументов отдельно. Не меняй глобальные Windows proxy settings ради удобства.

Программы без собственной поддержки прокси в MVP не поддерживаются. Не превращай раздел приложений в выбор EXE с ложным обещанием автоматической маршрутизации.

## 9. Закрепление версии компонента и обновления

`core.lock.json` фиксирует URL fork, полный source commit, версию IPC, версию AWG-модуля, версию сборочного toolchain, SHA-256 бинарника и состояние лицензии. Пока лицензия не выяснена — `license_status: blocked`, без фиктивного бинарника и хеша.

Нормальный выпуск содержит GUI и отдельный совместимый core, лицензии и уведомления. Источники core остаются в форке; клиент не импортирует произвольный HEAD и не скачивает исполняемый код с main при запуске.

Обновление upstream: fetch -> проверка diff и лицензий -> тесты ядра -> тесты контракта -> тесты Windows/сервера -> новый reviewable PR с обновлением lock -> release. Изменение лицензии или IPC блокирует автоматический выпуск.

Автообновление приложения не входит в MVP. Для первой версии достаточно страницы релизов и ручного обновления с проверкой происхождения и checksum. Не добавляй самозамену EXE из непроверенного URL.

## 10. Тесты и критерии приёмки

Пиши тесты до исправлений в парсерах, протоколах и state machine. Не заменяй проверки сети моками во всех сценариях. При этом публичный CI не должен зависеть от личного VPN пользователя.

| Проверка | Ожидаемый результат |
|---|---|
| Обычный запуск Windows 11 | Без UAC, службы и сетевого адаптера |
| Снимки сети до/после | Маршруты, DNS, WinINET/WinHTTP proxy и PAC не меняются из-за клиента |
| Запрос без прокси | Прежний путь соединения; приложение не перехватывает его |
| TCP через SOCKS5/HTTP | Успешный запрос через тестовый VPN-сервер |
| DNS домена назначения | Только через туннель; bootstrap endpoint учитывается отдельно |
| Endpoint недоступен/неверные ключи | Ошибка/ожидание, не ложный Connected и не DIRECT |
| Отказ во время потока | Поток закрыт/тайм-аут; новое соединение не уходит напрямую |
| Конфликт портов | Понятная ошибка, без убийства чужого процесса |
| `0.0.0.0` / `[::]` в настройках | Отклонено |
| UDP ASSOCIATE / BIND | Корректный unsupported response |
| Oversized `.vpn`, zlib bomb, неверные ключи | Ограниченное потребление памяти и понятная безопасная ошибка |
| Неизвестное поле/несколько Peer | Явная ошибка либо документированная проверенная поддержка |
| Disconnect/Quit/crash GUI | Нет оставшегося core/listener и утечек goroutine |
| 100 циклов Connect/Disconnect | Нет роста числа процессов/дескрипторов и зависания UI |
| Sleep/resume, смена Wi-Fi | Восстановление или понятная ошибка без прямого fallback |
| Профиль другого Windows-пользователя | Нет автоматического plaintext fallback при ошибке DPAPI |
| Логи, process args/env, commit, zip | Нет конфигураций и секретов |
| MockCore | Явно тестовый статус, не работает как реальный VPN |
| Реальный AWG 2.0 профиль | Handshake и запрос подтверждены либо честно «не проверено» |

Снимки сети можно делать read-only командами `Get-NetRoute`, `Get-NetAdapter`, `Get-DnsClientServerAddress`, `netsh winhttp show proxy` и чтением соответствующих пользовательских proxy settings. Учитывай независимые изменения DHCP/сети, а не сравнивай сырые timestamp побайтно.

Для сетевых acceptance-тестов заведи контролируемые HTTP/DNS endpoints и тестовый сервер с одноразовыми ключами. На физическом интерфейсе от core разрешены только ожидаемый VPN endpoint и документированный bootstrap DNS. В тестах различай трафик других процессов и самого клиента; не делай вывод «утечек нет» по одной проверке внешнего IP.

Пример ручной проверки с разрешённым пользователем диагностическим сервисом:

```powershell
curl.exe --noproxy "*" https://api.ipify.org
curl.exe --noproxy "" --socks5-hostname 127.0.0.1:1080 https://api.ipify.org
# Только если включён HTTP listener:
curl.exe --noproxy "" --proxy http://127.0.0.1:8080 https://api.ipify.org
```

Одинаковые адреса сами по себе не доказывают поломку: обычное соединение может уже идти через другой VPN/NAT. Проверяй реальный путь и контролируемые тесты. Не выключай чужой VPN автоматически.

## 11. CI, сборка и публикация

Нужны отдельные pipelines продукта и форка. До разрешения лицензии публичный pipeline продукта собирает только независимую оболочку и MockCore; компонент не скачивается, не модифицируется и не публикуется им.

После разрешения интеграции:

- `gofmt`, `go vet`, unit/contract/integration tests, fuzz smoke для конфигураций и прокси; race detector там, где поддержан toolchain. Не скрывай неподдержанный runner как успешный тест.
- `govulncheck` и secret scan закреплёнными версиями; лицензии прямых/транзитивных зависимостей и SBOM. Отдельно оценивай достижимость находок и не подавляй всё blanket-исключениями.
- Windows x64 build на Windows runner с нужным C toolchain для GUI. Headless-тесты UI не заменяют ручную проверку tray, DPI, DPAPI и Windows lifecycle.
- Actions закреплены полными commit SHA, `permissions: contents: read` по умолчанию. Write-permission только release job. Не выполняй чужой PR-код с секретами через `pull_request_target`.
- VPN-конфигурацию пользователя не добавляй в Actions secrets. Контролируемый integration lab, если нужен, должен иметь временные отдельно созданные ключи и не использовать production-сервер.
- Release: portable ZIP с GUI/core, README, LICENSE/THIRD_PARTY_NOTICES, версиями и SHA256SUMS. Не включай debug dumps, пользовательские данные и конфиги. Пока core заблокирован, выпускай только явно обозначенную демонстрационную оболочку либо не публикуй релиз.

Подпись Authenticode — отдельный этап с настоящим сертификатом. Не называй неподписанный EXE подписанным, не обещай отсутствие SmartScreen и не отключай защиту Windows. Установка Go/компилятора нужна разработчику, а не конечному пользователю.

Он **не** создаёт GitHub-репозитории, не скачивает код, не меняет execution policy и не устанавливает системные программы.

Дополнительные универсальные `security-best-practices`, `security-threat-model`, `gh-fix-ci` из `openai/skills` можно рассмотреть позднее. Они не обязательны для старта и **не входят** в установленный этим комплектом набор. Не загружай весь каталог навыков только ради нескольких функций.

## 13. Этапы выполнения

### Этап 0 — подготовка и лицензии

Проверь среду и существующие файлы; установи project-local skills. Повтори лицензионный аудит до создания репозиториев. Создай настоящий неизменённый fork и независимый продукт, если их ещё нет. Сохрани результаты API-проверки ownership/fork/visibility. Не выдавай плановые URL за созданные репозитории.

**Результат:** два проверенных репозитория либо точный блокер, проектные инструкции, лицензионный отчёт, корректный `.gitignore`. При нехватке прав не меняй архитектуру на копию вместо fork.

### Этап 1 — независимая оболочка

Создай архитектуру, контракт IPC, state machine, MockCore, окно/tray, профильные метаданные, DPAPI и тесты. При заблокированной лицензии это рабочий независимый этап, но не готовый VPN.

**Результат:** Windows-приложение с явным demo mode и без прямого сетевого прокси.

### Этап 2 — компонент

Только после лицензии: baseline-сборка, проверка Windows, исправления аудита, IPC mode, валидация конфигураций, lifecycle, DNS и fail-closed.

**Результат:** воспроизводимая сборка core с unit/integration tests и совместимым контрактом.

### Этап 3 — интеграция

Supervisor, handshake-based state, импорт клиентского профиля, соединение с тестовым сервером, затем добровольно предоставленным локальным профилем пользователя. Не проси вставлять приватный ключ в чат.

**Результат:** подтверждённые запросы SOCKS5/HTTP без изменения системной сети; список реально проверенных версий AWG.

### Этап 4 — удобство и отказоустойчивость

Помощник приложений, автозапуск opt-in, reconnect, sleep/resume, диагностика, DPI и ручная Windows-приёмка.

### Этап 5 — выпуск

Security review, license/dependency review, чистая сборка, CI и portable ZIP. Не выпускай компонент с нерешённой лицензией и не отмечай непроведённые тесты успешными.

После каждого этапа делай небольшой осмысленный commit. Не объединяй в один commit импорт upstream, большой рефакторинг и изменения GUI. Не отправляй PR автору upstream без отдельной задачи.
